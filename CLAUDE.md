# CLAUDE.md — паспорт проекта

## Что это
Бот-диспетчер выездной ветеринарной службы. Роли создают и распределяют заявки на выезд к животным. Внутренний инструмент клиники, не публичный сервис.

Целевая платформа — мессенджер **MAX** (аналог Telegram, РФ). Проект целиком на MAX. Изначально логика отрабатывалась на VK-прототипе (референс) — он выполнил свою роль и удалён из репозитория после переноса на MAX.

## Роли и права
- **dispatcher** (диспетчер) — создаёт заявки.
- **doctor** (врач) — принимает заявки, получает контакты после одобрения, закрывает с суммой чека.
- **manager** (управляющий) — права диспетчера + одобряет/отклоняет принятие врачом.
- **director** (директор) — всё вышеперечисленное + управление ролями, добавление/удаление сотрудников, привязка чатов к городам.

Права централизованы в `src/domain/models.ts` (функции `can*`). Менять права — только там.

## Создание заявки
Диспетчер выбирает город (направление) КНОПКОЙ, а не вводит текстом — кнопки строятся на лету из `city_chats` и показывают только направления, где заданы ОБА чата (работа + управление). Остальные поля (дата, животное, проблема, оговорённая цена, контакты клиента) — текстом по шагам (`domain/draft.ts`, `Draft.city` хранится отдельно от текстовых `FIELDS`). Если ни одного полностью настроенного направления нет — заявку начать нельзя, диспетчер получает отказ с просьбой обратиться к директору. Масштабирование направлений — только через `/привязать <Город> работа|управление` в самом чате, без правок кода. НЕ возвращать ввод города текстом.

## Жизненный цикл заявки
`open` → врач принял → `taken` → управляющий/директор решает:
- **Одобрить** → `approved` (контакты уходят врачу в личку) → врач закрыл → `closed`
- **Отклонить** → снова `open` (заявка свободна). Отклонить можно ТОЛЬКО пока `taken` (до одобрения).

## Ключевое требование: видимость (НЕ нарушать)
- Контакты клиента НИКОГДА не попадают в общий чат. Только в личку врачу и только после одобрения.
- На каждый город — ДВА чата:
  - **рабочий чат** (врачи): нейтральные карточки, кнопка «Принять». Врачи НЕ видят имя принявшего и сумму чека.
  - **управленческий чат** (директор/управляющий/диспетчер): карточки с деталями — кто принял, кнопки Одобрить/Отклонить, сумма чека.
- Один мессенджер-чат показывает всем участникам ОДИН текст — разной видимости внутри одного сообщения быть не может. Поэтому детали идут в отдельный управленческий чат, а не «скрываются» в общем.

## Архитектура (соблюдать строго)
Чистая архитектура. Стрелки зависимостей: адаптеры → домен. Домен про мессенджер НЕ знает.

- `src/domain/` — модели, правила, сервисы. НЕ импортирует ничего из `adapters/`.
- `src/db/` — схема SQLite и репозитории. Граница snake_case (БД) ↔ camelCase (код) в функциях `to*`.
- `src/ports/Messenger.ts` — интерфейс мессенджера. Домен общается с миром только через него.
- `src/adapters/max/` — MAX-реализация.

Правило: любая логика (роли, статусы, захват, одобрение) живёт в домене и НЕ дублируется в адаптерах. Адаптер только переводит вызовы порта в API мессенджера.

## Атомарность (критично)
Захват/одобрение/отклонение/закрытие — через один SQL UPDATE с условием на текущий статус (`WHERE id=? AND status='...'`). Это защита от гонки, когда несколько человек жмут кнопку одновременно. НЕ заменять на «прочитать → проверить в JS → записать».

## Стек
- TypeScript + Node.js (ESM, `"type": "module"`). В импортах указывать расширение `.js` даже для `.ts`-файлов (требование NodeNext).
- SQLite через `better-sqlite3` (синхронный, транзакции).
- MAX: `@maxhub/max-bot-api`.
- Деньги — в копейках, целым числом. Никаких float.

## MAX: транспорт (важно, не сломать)
- API-домен: **`https://platform-api2.max.ru`** (не старый `platform-api.max.ru`).
- Токен — только в заголовке `Authorization`, не в query.
- Нужен сертификат Минцифры: файл `certs/russian_trusted_root.pem`, подключается через `NODE_EXTRA_CA_CERTS` в скрипте запуска (см. package.json). Без него TLS к MAX не проходит.
- Токен бота — в `.env` (`MAX_TOKEN`). `.env` в git НЕ коммитится.

## Правила работы
- Коммит после каждого крупного блока (не после каждой мелкой правки). Сообщения коммитов по-русски, по существу.
- НЕ коммитить: `.env`, `data.db*`. Сертификат в `certs/` коммитить МОЖНО (публичный).
- После значимых изменений обновлять `PROGRESS.md`.
- Менять схему БД на этапе разработки: пересоздание базы (`rm data.db*` + перезапуск). На проде — миграции (позже).
- Проверять компиляцию: `pnpm exec tsc --noEmit`.

## Команды
- Запуск: `pnpm dev:max`
- Наполнить тестовыми данными: `pnpm seed` (см. `scripts/seed.ts` — отдельная БД, `data.db` не трогает)
- Проверка типов: `pnpm exec tsc --noEmit`
- Тест гонки: `pnpm exec tsx test-claim.ts`

## Окружение
Редактор может использовать свою (более старую) версию TypeScript для подсветки — например 6.x, — а проект собирается на TypeScript 7 (`package.json` → `devDependencies.typescript`). При расхождении подсветки и реальных ошибок истина всегда за `pnpm exec tsc --noEmit`, не за редактором. Если редактор подсвечивает ошибки, которых `tsc --noEmit` не показывает (частая причина — устаревший кэш TS-сервера после правок в другом чате/сессии), помогает Reload Window или Command Palette → «TypeScript: Select TypeScript Version» → «Use Workspace Version».

## Особенности @maxhub/max-bot-api (грабли)
- `editMessage` адресует сообщение глобально по `messageId`, `chat_id` не нужен (в `MaxAdapter` параметр `chatId` в `editGroupCard`/`editManageCard` не используется, помечен `_`).
- Личка шлётся через `sendMessageToUser(userId)`. В нашей модели `dmChatId` ХРАНИТ MAX `userId` (не chatId лички). При онбординге (`bot_started`) сохраняем `userId` в `dmChatId`.
- id отправленного сообщения = `message.body.mid`.
- Баг библиотеки: в событии `message_created` тип `ctx.user` резолвится как `undefined`, хотя рантайм подставляет `message.sender`. Брать отправителя напрямую: `ctx.message.sender?.user_id` и `.name`.
- Личку от группы отличаем по `ctx.message.recipient.chat_type === 'dialog'` (значения: `'dialog' | 'chat' | 'channel'`).
- Кнопки: `payload` — строка `"действие:значение"`, делить по ПЕРВОМУ `:` через `indexOf`/`slice` (не `split(':')`, не по пробелам). `take`/`approve`/`reject`/`close:<id>`, `city:<Город>` (название направления может содержать пробелы). `callback_id` = `eventId` для `answerOnCallback`.
- Клавиатуры: `attachments: kb ? [kb] : []` — ОБЯЗАТЕЛЬНО пустой массив, не `undefined`. При `editMessage` поле со значением `undefined` выпадает из `JSON.stringify` и пропадает из тела запроса целиком — MAX трактует его отсутствие как «вложения не менять», старая клавиатура остаётся висеть (баг, наступили и починили в `MaxAdapter`).
- Транспорт: разработка на long polling; в каждой группе бот должен быть АДМИНОМ, иначе не видит сообщения группы; добавление бота в группы должно быть разрешено в кабинете бота (business.max.ru).
