## Предстоящие правки (согласовано с заказчиком, НЕ начато)

1. Отмена ОТКРЫТОЙ (непринятой) заявки — новый статус `cancelled`. Доступно диспетчеру/управляющему/директору. Решение по UI: заявка при создании постится СРАЗУ и в управленческий чат (не только в рабочий), там кнопка «Отменить» для открытой заявки — сейчас управленческая карточка появляется только после принятия врачом, это меняется. Отменённые заявки хранятся со статусом `cancelled`.

2. Вакцинация становится полноценной заявкой с тем же жизненным циклом (рабочий чат → принятие → одобрение → закрытие). Решение: объединить заявку и вакцинацию в ОДНУ сущность с полем `type` (`'request'|'vaccination'`); у вакцинации доп. поля — какая вакцина, дата следующей вакцинации. Хранение: две таблицы, не зависящие друг от друга (то есть переход не сливает `requests` и `vaccinations` в одну таблицу — механика заявки распространяется на вакцинацию отдельным путём). Команда `/вакцина` создаёт заявку типа `vaccination` с теми же полями заявки + вакцина.

3. Врачу после одобрения заявки (обычной и вакцины) дублируется ВСЯ карточка заявки целиком (все поля + контакты), а не только текст с контактами, как сейчас.

4. В заявки добавить новое поле адрес клиента. Это поле врачи должны видеть и до принятия заявки (там диспетчер не будет указывать номер квартиры). А в поле контакты будет дублироваться полный адрес, поэтому там в тексте надо написать что это не только номер телефона, но и полный адрес (его как и прежде врачи видят только после одобрения).

Деплой правок — как обычно: `git pull` + `pnpm build` + `systemctl restart vet-bot`, когда всё готово и проверено.

## Важные решения (не переигрывать без причины)
- Один бот на все города (лимит MAX — 5 ботов на организацию; «бот на город» отвергнут).
- Два чата на город вместо личек управляющим (привязка «чат→город», а не «человек→город»).
- Отклонить = освободить заявку (одна операция, не отдельные «отклонить» и «отменить»).
- Отклонение возможно только до одобрения.
- VK-прототип использовался как референс на этапе переноса логики на MAX; после переноса — удалён из репозитория (проект целиком на MAX).
- Разработка MAX-бота ведётся на Long Polling (официально разрешён для разработки; библиотека `@maxhub/max-bot-api` умеет только его). В production MAX Long Polling не рекомендует — нужен Webhook.
- Библиотека webhook НЕ поддерживает (проверено разведкой пакета). Поэтому на этапе деплоя — отдельный блок работы: Express-обёртка принимает POST от MAX, nginx даёт HTTPS, подписка регистрируется через `POST /subscriptions`. Это ~день работы на деплое, домен и адаптер сообщений при этом не меняются.
- Домен для webhook: поддомен сайта заказчика (напр. `bot.клиника.ru`) → указывает на VPS. Отдельный домен покупать не нужно, если у заказчика есть свой.
